## Mechanisms worth stealing (ranked)

1. **Slippage-then-fees fill model, with cash-constrained partial fill** — `buy_nb`/`sell_nb` in `vectorbt/portfolio/nb.py:72` and `:215`. Fill price is `adj_price = price * (1 + slippage)` for buys, `price * (1 - slippage)` for sells (pure fraction, not spread-based). Cost = `req_cash = size * adj_price`, `fees = req_cash * fees_pct + fixed_fees`. If `total_req_cash > cash_limit`, the order is **not rejected but downsized**: `max_req_cash = (cash_limit - fixed_fees) / (1 + fees)`, then `final_size = max_req_cash / adj_price` — i.e. it solves backward for the largest size affordable including proportional+fixed fees, respecting `size_granularity` (lot-size rounding via floor-division). Directly reusable for `execution-cost-model` and `paper-fill-simulator`: real venues also silently truncate the fillable size under margin/lot constraints rather than hard-rejecting.
2. **Enumerated order-rejection reasons, not a bool** — `OrderStatusInfoT` in `vectorbt/portfolio/enums.py:502`: 14 explicit codes (`SizeNaN`, `PriceNaN`, `NoCashShort`, `NoCashLong`, `NoOpenPosition`, `MaxSizeExceeded`, `CantCoverFees`, `MinSizeNotReached`, `PartialFill`, `RandomEvent`, ...). Every unfilled order carries one of these via `order_not_filled_nb` (`nb.py:65`). This is a ready-made vocabulary for `order-reject-reason` (execution-venue-adapter block) — our blueprint currently says only "classified: balance, rate limit, price band, size step, outage"; vectorbt's list adds `CantCoverFees` (size covers notional but not fees) and `MinSizeNotReached` as distinct causes worth keeping separate from a generic "balance" bucket.
3. **`RandomEvent` rejection probability as a first-class fill parameter** — `sell_nb`/`buy_nb` accept `reject_prob` (see `_log_fields` in `portfolio/enums.py:1773` `req_reject_prob`) so a backtest can inject a stochastic reject rate independent of cash/size logic. Useful for `execution-cost-model` to simulate exchange-side flakiness (rate limits, transient 5xx) without conflating it with slippage.
4. **Order/trade separation via two record schemas plus FIFO matching** — `order_dt` (one row per filled order: `nb.py` enums around line 1773) is distinct from `trade_dt` (`portfolio/enums.py:_trade_fields`, fields `id, col, size, entry_idx, entry_price, entry_fees, exit_idx, exit_price, exit_fees, pnl, return, direction, status, parent_id`). `get_exit_trades_nb` (`portfolio/nb.py:6075`) walks a column's orders in ascending id order and matches sells against the oldest open long lots (FIFO), splitting a single order across multiple trade records when it only partially closes an accumulated position, and stamping every resulting trade with a `parent_id` linking round-trips that share one continuous position. This is exactly the `fill-reconciler` → `closed-trade` boundary we need: a `fill` is not a `closed-trade`, and one fill can close/open multiple logical trades.
5. **Column-indexed record maps instead of per-symbol object lists** — `col_map_nb` (`records/nb.py:101`) builds `(col_idxs, col_lens)`: a single flat array of all records across every symbol/column, with an index that lets any downstream function slice "just this column's records" in O(1) without scanning. This is the `episodic-trade-store`/`instruction-archive` storage pattern to steal: store all trade-episodes in one append-only array keyed by symbol, not N per-symbol Python lists — cheaper to journal, easier to hash-chain (ties to `journal-integrity-checker`).
6. **Walk-forward split as three primitives, not one function** — `generic/splitters.py`: `RangeSplitter.split` (`:109`, arbitrary/custom windows), `RollingSplitter.split` (`:185`, fixed-length rolling window), `ExpandingSplitter.split` (`:234`, start pinned at 0, end grows). All three funnel into `split_ranges_into_sets` (`:21`) which then divides each window into ordered sets by fraction or absolute length (`set_lens=(0.5, 0.25)` → 50% train / 25% validation / 25% remainder, in time order, `left_to_right` controls whether the *last* or *first* set is the flexible-length one). This is a clean reference for `walk-forward-splitter`: today our blueprint just says "split history into training windows that never overlap the test window" — vectorbt shows the split needs to support rolling AND expanding AND custom-boundary modes as one contract, and that "no overlap" plus "ordered" are the actual invariants worth unit-testing.
7. **Performance-metric formulas with exact denominators, annualization explicit** — `returns/nb.py`: Sharpe (`:338`) = `mean(r - risk_free) / std(r - risk_free, ddof=1) * sqrt(ann_factor)`, returns `np.inf` when std is exactly 0 rather than NaN or a crash. Sortino (`:411`) divides by **downside deviation only** (`downside_risk_1d_nb` at `:378`: `sqrt(nanmean(min(r - required_return, 0)**2)) * sqrt(ann_factor)`), Calmar (`:254`) divides annualized return by max drawdown, Omega (`:285`) and tail ratio (`:569`) and CVaR (`:634`, mean of returns below the 5% empirical quantile) are all present with the same 1d/2d/rolling three-way pattern. Directly reusable formulas for `backtest-scorer`, worth citing verbatim rather than re-deriving from memory.
8. **Drawdown as its own record type with recovery tracked separately from decline** — `generic/drawdowns.py:236` `Drawdowns(Ranges)`. Fields include `decline_duration` (`:366`), `recovery_duration` (`:378`), `recovery_duration_ratio` (`:392`, recovery time / decline time — a speed-of-healing metric), and a live `active_drawdown`/`active_duration` (`:407`,`:425`) for a drawdown still in progress (not yet closed). Worth stealing the *recovery-vs-decline asymmetry* as an explicit field for `usdt-pnl-accountant`/`peak-excursion-tracker` rather than only tracking magnitude.
9. **Group-level shared cash accounting** — `cash_in_sim_order_nb` (`portfolio/nb.py:6745`) and `value_in_sim_order_nb` (`:6808`) compute cash/value at the *group* level so multiple symbols can share one capital pool with an explicit `call_seq` (the order in which columns are visited each bar) rather than each symbol having an independent, siloed balance. Relevant to `capital-allotment-reader`/`cross-segment-exposure-watch`: if we ever let bots within one segment share a capital pool, this call-sequence-plus-shared-ledger pattern is the reference, not naive per-bot balances.

## New part proposals

- **`fill-cost-downsizer`** — block: `backtesting`. consumes: `order-request`, `cost-estimate`, `account-balance`. produces: `sized-order` (or a NEW `partial-fill-notice` if we want the downsize event itself journaled distinctly from a plain fill). One-line responsibility: when a simulated or paper order's notional-plus-fees exceeds available cash, shrink it to the largest affordable size instead of rejecting outright. Evidence: `portfolio/nb.py:buy_nb:157-177`.
- **`round-trip-trade-matcher`** — block: `portfolio-state`. consumes: `fill`. produces: `closed-trade` (already exists as a data type; this names the missing part that builds it via FIFO lot matching rather than assuming 1 fill = 1 trade). One-line responsibility: match closing fills against the oldest open lots of a position so partial closes and re-adds resolve into correctly-sized, correctly-linked closed trades. Evidence: `portfolio/nb.py:get_exit_trades_nb:6075`.
- **`drawdown-recovery-tracker`** — block: `observability`. consumes: `usdt-pnl-statement` or `account-balance`. produces: NEW `drawdown-episode` (decline duration, recovery duration, recovery-duration-ratio, whether still active). One-line responsibility: track each drawdown from its peak through recovery (or ongoing) as its own record, distinct from `peak-excursion` which is per-position not per-equity-curve. Evidence: `generic/drawdowns.py:236-494`.

## Anti-patterns seen

- **`Portfolio` god object** — `portfolio/base.py:1498`, a single class with **95** methods/properties in a 247KB file: simulation entry points (`from_signals`, `from_orders`, `from_holding`, ...), every stats accessor, every plotting method, cash/value/return accessors, all inherited/mixed into one object. Violates T-6 (grow by adding parts, never make one part cleverer) hard — this is the textbook "welded together" part the rule warns about. We must not port this shape; each responsibility (simulate, score, plot, journal) is a separate part in our design already, and this repo is the cautionary example for why that separation matters at scale.
- **Numba kernels are 290KB of positional-only functions with 15+ parameters** (`portfolio/nb.py`, e.g. `simulate_from_orders_nb` at `:1353` takes `target_shape, group_lens, init_cash, call_seq, size, price, fees, fixed_fees, slippage, min_size, max_size, size_granularity, reject_prob, lock_cash, allow_partial, raise_reject, log, val_price, ...`). No named-parameter object; every call site must remember positional order. Contradicts T-1 (uniform part shape/interface) — a part whose call signature this wide is not the same shape as any other part and cannot be composed generically.
- **Global mutable numba cache/state via `@njit(cache=True)`** across hundreds of functions with implicit compilation cache keyed on argument dtypes — not an in-process data race, but it means "the same function" can silently behave differently machine-to-machine depending on cached bytecode. Not directly a T-3 violation (no off-state to release) but worth flagging: any part we compile/cache must be able to prove its behavior is reproducible, not just fast.

## Not useful here

vectorbt has no broker/exchange adapters, no live data feed, no order routing, no async event loop — it is purely an offline vectorized simulator plus a stats/records layer, so anything about `execution-venue-adapter`, `market-data-feed`, or real-time control-plane behavior (T-2/T-3) has no reference implementation here. Its examples and defaults are equities/FX-oriented (daily/OHLC bars, no funding rate or liquidation-price concepts), so segment-specific mechanisms (funding forecasting, liquidation cascades, options implied-vol) are absent. Skipped entirely: `vectorbt/indicators/` (technical-indicator factory, not decision logic), `vectorbt/labels/` (ML labeling helpers), `vectorbt/messaging/` (Telegram bot glue), `vectorbt/data/` (data-source download wrappers, not a live feed), and the `rust/`, `benchmarks/`, `apps/` top-level dirs (packaging/perf-test scaffolding, no trading logic) — all out of scope for mechanisms worth stealing.
